# Questions

1. Synchronous vs asynchronous replication: what does each guarantee at failover, and what does each cost?
2. Define read-your-writes and monotonic reads, with an implementation of each.
3. Walk through a failover. Where can data be lost, and what is split brain?
4. Sharding: range vs hash, how to pick a shard key, and what resharding costs.
5. PACELC: classify Postgres with async replicas, DynamoDB, Spanner, Cassandra.
6. You must run Postgres for a service with RPO = 0 and RTO < 60 s in one region. Describe the setup.

## Model answers

1. Synchronous: an acknowledged write is on at least two nodes, so promoting that replica loses nothing (RPO 0); every commit waits for a network round trip and a replica fsync, and if the only synchronous replica is down, writes stall (hence quorum commit: any 1 of 2). Asynchronous: lowest latency and no dependency on replicas; a failover loses whatever was not shipped (RPO = lag), and replicas serve stale reads.
2. Read-your-writes: after a user writes, that user's reads reflect the write. Implementation: return the commit LSN to the client (cookie/token); route reads to a replica that has replayed at least that LSN (or wait for it with a timeout), else to the primary; simpler variant: read from the primary for N seconds after a write. Monotonic reads: a user never sees time go backwards. Implementation: track the highest LSN the session has observed and require it of any replica, or pin the session to one replica.
3. Detect failure (timeouts: false positives are the risk) → choose the most advanced replica → promote it and bump the timeline/epoch → repoint clients (DNS, proxy, or service discovery) → rebuild or rewind the old primary as a replica. Loss: with async replication, the writes the old primary acknowledged but had not shipped; they must be discarded on the old node. Split brain: the old primary is alive but partitioned and keeps accepting writes while the new one does too: two diverging histories. Prevent with fencing: leases and epochs checked by clients and storage, a consensus-backed leader lock (Patroni + etcd), shooting the old node.
4. Range sharding keeps keys ordered (range scans, time series) and risks hot ranges and uneven shards; hash sharding spreads load evenly and loses range scans. Shard key: high cardinality, even access, present in most queries, and the natural transaction boundary (tenant id, user id) so that most transactions stay on one shard; avoid monotonically increasing keys with range sharding. Resharding moves data while serving traffic: use many virtual shards mapped to nodes (move a shard, not individual keys), copy then switch with dual writes or log shipping, and expect cross-shard transactions and queries to be the lasting cost.
5. Postgres + async replicas: under partition the primary side stays consistent and the minority is unavailable for writes (PC); else it favours latency over consistency on replicas (EL): PC/EL. DynamoDB: available under partition; eventually consistent reads by default for latency: PA/EL (strongly consistent reads optional). Spanner: consistent under partition, and pays latency for consistency always (TrueTime commit wait): PC/EC. Cassandra: tunable, default PA/EL.
6. Three nodes in three availability zones managed by a consensus-backed failover manager (Patroni with etcd, or a managed service with synchronous standbys); synchronous quorum commit (`ANY 1` of two standbys) for RPO 0; automated promotion with fencing of the old primary; clients connect through a proxy or pooler that follows the leader (PgBouncer/HAProxy with health checks); continuous WAL archiving and base backups to object storage for point-in-time recovery, with restore tested; alert on replication lag, replication slots and failover events; a failover drill every quarter to prove the 60 seconds.
