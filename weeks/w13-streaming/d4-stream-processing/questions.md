# Questions

1. Event time vs processing time: give one metric that is wrong if computed on processing time, and why.
2. What is a watermark? What do you trade when you make the out-of-order bound larger or smaller?
3. Tumbling, sliding and session windows: define each with one use case.
4. How does Flink get exactly-once state? What more is needed for exactly-once output to Kafka, and to Postgres?
5. Lambda vs Kappa architecture. Why has Kappa mostly won, and when is a batch layer still right?
6. Design in 3 minutes: ad-click aggregation, 100 B events/day, per-campaign counts within 30 s, billing-grade accuracy by the next day.

## Model answers

1. "Orders per minute" during an outage of the ingestion path: with processing time, the backlog is counted in the minutes it is finally processed, showing a dip then a spike that never happened; a replay gives yet another answer. Event time gives the same result whenever and however often you compute it. Processing time is right only for questions about the system itself (throughput, lag).
2. A monotone estimate "all events with time ≤ W have arrived". Larger bound: more complete windows, later results, more state held. Smaller bound: faster results, more late events to handle (updates or side output). It is a heuristic: some data will still be later, hence allowed lateness and a dead-letter path.
3. Tumbling: fixed, non-overlapping (clicks per minute, billing periods). Sliding: fixed length, advancing by a smaller step, overlapping (5-minute moving average updated every 30 s; fraud velocity features). Session: per key, closed by a gap of inactivity (user sessions, a robot episode); windows merge when a late event bridges two.
4. Asynchronous barrier snapshots (Chandy–Lamport): barriers flow with the data; each operator snapshots its state when the barrier has arrived on all its inputs; source offsets are part of the checkpoint. Recovery = restore the last complete checkpoint and replay from its offsets. For Kafka output: a transactional producer whose transaction is committed only when the checkpoint completes (two-phase commit), with consumers in `read_committed`. For Postgres: an idempotent upsert keyed by (window, key) or an event id, or store results and offsets in one transaction.
5. Lambda: a batch layer (complete, slow) plus a speed layer (approximate, fast), merged at query time: two codebases that must agree. Kappa: one streaming pipeline; reprocessing = replay the log through a new version of the same code. It won because logs became long-retained (tiered storage) and stream engines got exactly-once state. A batch layer is still right for reconciliation against a source of truth (billing), for heavy backfills cheaper in batch, and when the logic needs global passes.
6. ~1.2 M events/s average, ~3.5 M at peak; 1 KB each → over 1 GB/s: Kafka with hundreds of partitions, keyed by ad or campaign id (salt the hot ones and re-aggregate). Clients send click id + event time; dedupe by click id in a keyed-state TTL store. Flink job: event-time tumbling windows of 10–60 s, watermark bound of a few seconds, early results every few seconds, allowed lateness of minutes with updates, late events to a side topic. Sink: OLAP store (ClickHouse/Druid/Pinot) with idempotent upserts keyed by (campaign, window). Billing: raw events also land in object storage; a nightly batch job recomputes exact counts with fraud filtering and reconciles; discrepancies above a threshold alert. Mention: exactly-once via checkpoints + idempotent sink, lag and watermark-delay alerts, replay plan, cost of cross-AZ traffic.
