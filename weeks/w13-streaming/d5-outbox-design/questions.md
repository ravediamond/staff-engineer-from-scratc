# Questions

1. What is the dual-write problem? Why can a try/except with a retry not fix it?
2. Describe the outbox pattern with CDC end to end. What are the delivery semantics at each hop?
3. BACKWARD vs FORWARD compatibility: which side deploys first in each, and which changes are always safe?
4. "Exactly-once": what does Kafka guarantee with transactions, and what remains your job?
5. Kafka vs RabbitMQ/SQS vs Pub/Sub/Kinesis vs Postgres `SKIP LOCKED`: one sentence each on when to choose it.
6. A poison message makes a consumer crash in a loop. Design the retry and dead-letter path without blocking the partition forever and without losing per-key order where it matters.

## Model answers

1. One logical change must reach two systems that share no transaction (database and broker). Any order of the two writes has a crash window that leaves them disagreeing, and the process that could retry is the one that died: after restart it does not know a send is missing. Retrying in-process only narrows the window. The fix is to make one system the source of truth and derive the other from its log.
2. The service writes the business row and an outbox row in one local transaction (atomic). Debezium (Kafka Connect) reads the database's replication log (WAL/binlog), so it sees exactly the committed changes, in commit order, and produces them to a topic keyed by aggregate id, storing its log position in Kafka: at-least-once into Kafka (a connector restart can re-emit). Consumers process then commit: at-least-once again, made effectively-once by an idempotent effect keyed on the event id in the same transaction. Outbox rows are deleted after capture or expire.
3. BACKWARD (new readers read old data): upgrade consumers first, then producers; the default in Confluent's registry; needed anyway to replay old data. FORWARD (old readers read new data): producers first. Always safe: adding an optional field with a default; removing a field that has a default (FULL). Never: changing a type, renaming without an alias, reusing a Protobuf tag, making an optional field required. Breaking change → new topic version (`orders.v2`), dual-publish, migrate consumers, retire v1.
4. Transactions make a set of writes to several partitions, plus the consumer-offset commit, atomic and visible only to `read_committed` readers: exactly-once for consume-transform-produce chains INSIDE Kafka (Kafka Streams `exactly_once_v2`, Flink's two-phase-commit sink). Outside Kafka nothing is guaranteed: an email, an HTTP call or a row in Postgres needs an idempotency key or a transaction that also stores the offset. End-to-end exactly-once is a property of the whole pipeline.
5. Kafka: high-throughput ordered log with replay and many independent consumer groups; operational weight. RabbitMQ/SQS: task queues with per-message ack, routing and delays, little or no replay: simplest for background jobs. Pub/Sub and Kinesis: managed logs when you are on that cloud and do not want to run brokers (Pub/Sub: per-message ack, ordering keys; Kinesis: shards). Postgres `FOR UPDATE SKIP LOCKED`: a few hundred jobs per second with transactional enqueue and no new infrastructure: often the right first answer. (Redpanda: Kafka API, simpler operations; Pulsar: storage/compute separation and multi-tenancy; NATS JetStream: lightweight.)
6. Classify errors: non-retryable (bad schema, validation) go straight to the DLQ with the original topic/partition/offset, error and headers. Retryable: a few in-place retries with backoff, then publish to a retry topic with a delay (`orders.retry.5s`, `.1m`, `.10m`), commit and move on; after the last tier, DLQ + alert + a replay tool. Where order matters per key, moving one message aside lets later events of that key overtake it: record the key as "blocked" and route its later events to the same retry path, or stop the partition and page. Monitor DLQ depth and age; a DLQ nobody reads is data loss with extra steps.
