# Questions

1. Derive the KV-cache size per token and the maximum concurrency of a model on a GPU. What caps batch size in practice?
2. Why is GPU utilisation a bad autoscaling signal for LLM servers? Name three good ones and how they reach the HPA.
3. Break down the cold start of a 70B replica and give four ways to shorten it. When is scale-to-zero acceptable?
4. Why not put a plain Service (round-robin) in front of vLLM pods? What does an inference-aware gateway look at?
5. You must serve 200 fine-tuned LoRA adapters of one base model. Design the serving layer.
6. Which pieces would you name for: single-node serving, multi-node serving of one huge model, distributed fine-tuning, quotas? (One Kubernetes-native project each.)

## Model answers

1. Each layer caches a key and a value vector per KV head per token: 2 × layers × kv_heads × head_dim × bytes (fp16 = 2). Llama-3-8B: 2 × 32 × 8 × 128 × 2 = 128 KiB/token, about 1 GiB per 8k-token sequence; a 70B model (80 layers): 320 KiB/token. Concurrency = (GPU memory − weights − activations/overhead) ÷ (context × KV per token). Memory for KV, not FLOPs, usually caps the batch; hence paged KV allocation (vLLM's PagedAttention), context limits, prefix sharing, quantised KV and offloading.
2. Continuous batching keeps the GPU busy at any load above zero, so utilisation reads ~100% with 1 or 50 sequences: it cannot tell "busy" from "overloaded" and never signals scale-down. Good signals: number of requests waiting (vLLM exports `num_requests_waiting`), KV-cache usage, and latency SLO metrics (TTFT p95, queue time). They reach the HPA as custom/external metrics through Prometheus Adapter or KEDA; scale-up fast with headroom (replicas take minutes), scale-down slowly.
3. Node provisioning (2–5 min for a GPU node, when capacity exists) + image pull (CUDA images are 10+ GB) + weight download (140 GB) + load to GPU memory + warm-up. Shorten: keep warm spare nodes or a minimum replica count; pre-pull images (DaemonSet, node image); cache weights on node-local NVMe or a shared read-only volume and stream-load safetensors; smaller or quantised artefacts; snapshot/restore of a loaded process where available. Scale-to-zero only for small models or rarely used internal ones where a cold first request is acceptable; never for an interactive SLO.
4. Round-robin ignores state that changes latency by an order of magnitude: queue length and KV-cache pressure of each replica, which replica already holds the request's prompt prefix in cache, and which has the requested LoRA adapter loaded. The Gateway API Inference Extension adds an `InferencePool` and an endpoint picker that scores replicas on those signals, plus request priority (shed batch before interactive). Long-lived streaming responses also make connection-level balancing uneven.
5. One base model in memory per replica, adapters loaded dynamically (vLLM and others batch requests for different adapters together); each adapter is tens to hundreds of MB. An adapter registry maps adapter id → artefact, base model, version. Route with adapter affinity so each replica keeps a bounded hot set (LRU) and cold loads are rare; pre-load the top adapters; pin the very hot tenants to dedicated replicas or serve them merged into the weights (fastest, no multiplexing). Limit loaded adapters per replica for memory, meter per tenant, and canary new adapter versions behind the eval gate.
6. Single-node serving: vLLM behind KServe (`LLMInferenceService`) or the vLLM production-stack chart, with the Inference Gateway. Multi-node serving of one model: LeaderWorkerSet (a leader plus N workers scaled as one unit). Distributed fine-tuning: Kubeflow Trainer `TrainJob` (on JobSet); KubeRay when the workload is Ray-native. Quotas and fair sharing: Kueue. GPU plumbing: NVIDIA GPU Operator (driver, device plugin or DRA driver, MIG manager, DCGM exporter). Versions move fast: check the project pages before quoting them.
