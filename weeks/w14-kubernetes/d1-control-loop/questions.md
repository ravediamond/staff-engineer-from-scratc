# Questions

1. What happens between `kubectl apply -f deployment.yaml` and a container running? Name each component and what it writes.
2. Level-triggered vs edge-triggered: define both and say why Kubernetes controllers are level-triggered.
3. What are informers, the local cache, the work queue and resync for?
4. What is an operator? Sketch the reconcile loop of a `ModelDeployment` operator (weights in object storage, N replicas on GPUs).
5. Two controllers fight over the same field (HPA and a GitOps tool both set `replicas`). What do you see and how do you fix it?
6. Why is etcd behind the API server a consensus system, and what happens to the cluster when etcd loses quorum?

## Model answers

1. kubectl sends the object to the API server: authentication, authorization (RBAC), admission (mutating then validating webhooks), validation, then it is persisted in etcd. The Deployment controller sees it and creates a ReplicaSet. The ReplicaSet controller creates Pod objects with no node. The scheduler filters and scores nodes and writes the binding (`spec.nodeName`). The kubelet on that node sees its pod, asks the container runtime (containerd) to pull the image, sets up the network through CNI and volumes through CSI, starts containers, runs probes and writes pod status. When the pod is Ready, the EndpointSlice controller adds its IP to the Service's endpoints and kube-proxy (or the CNI dataplane) programs the node rules.
2. Edge-triggered: act on each change event ("a pod was deleted → create one"). Level-triggered: act on the current state ("there are 2, I want 3 → create one"), with events used only to know when to look. Events can be lost (controller down, watch dropped), duplicated or reordered; a level-triggered loop converges anyway and heals after any crash, which is what makes the system self-repairing.
3. An informer does one LIST then a WATCH on a resource type, keeps a local read-only cache so controllers do not query the API server for every read, and calls handlers on changes. Handlers put the object's key in a rate-limited work queue that deduplicates and retries failed keys with backoff. Workers pop keys and call reconcile, reading from the cache. A periodic resync re-enqueues everything to catch anything missed.
4. A custom resource definition plus a controller. `ModelDeployment{model URI, replicas, GPU type, runtime}`. Reconcile(key): read the CR; if it is being deleted, clean up and remove the finalizer; ensure a Deployment (or LeaderWorkerSet) exists with the right image, GPU request, model-cache volume and init step that fetches weights; ensure a Service and an autoscaler object; set owner references so deletion cascades; compare, patch only differences; write status (ready replicas, loaded model version, conditions); requeue with backoff on error. No step assumes the previous run finished.
5. The field flips back and forth: replicas jump, rollouts restart, the GitOps tool reports permanent drift. One owner per field: leave `replicas` out of the manifest managed by GitOps (or tell Argo CD to ignore that field) when an HPA owns it. Server-side apply's field managers make such conflicts explicit.
6. All cluster state lives there and controllers on several machines act on it; without linearizable writes two schedulers could bind the same pod differently or a stale leader could keep acting. etcd uses Raft: 3 or 5 members tolerate 1 or 2 failures. Without quorum the API server becomes read-only at best: nothing can be created, scheduled or healed, but running pods keep running because kubelets and the dataplane work from their last known state.
