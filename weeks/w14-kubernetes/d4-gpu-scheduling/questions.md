# Questions

1. Why does distributed training need gang scheduling, and where is it implemented (Kueue, Volcano, scheduler plugins)?
2. Explain Kueue's objects: ResourceFlavor, ClusterQueue, LocalQueue, cohort, borrowing, preemption. What does Kueue NOT do?
3. Device plugin vs DRA: what can a ResourceClaim express that `nvidia.com/gpu: 1` cannot?
4. MIG vs MPS vs time-slicing: isolation, use case, and what breaks.
5. "40% GPU utilisation, yet teams wait days for GPUs." Give five causes and the fix for each.
6. Training on spot GPUs: what must be true of the job, and how do you choose the checkpoint interval?

## Model answers

1. A distributed job (DDP, FSDP, MPI) needs all its workers to start; the default scheduler binds pods one by one, so two jobs can each get part of their pods and block each other while holding GPUs. Gang (all-or-nothing) scheduling admits a job only when the whole pod group fits. Kueue does it at admission (the job stays suspended until its quota and, with topology-aware scheduling, its placement are available); Volcano and YuniKorn are batch schedulers with PodGroups; the coscheduling plugin adds a Permit-stage wait to the default scheduler. Kubeflow Trainer's TrainJob (built on JobSet) is the unit they admit.
2. ResourceFlavor: a kind of capacity (H100 on-demand, A10 spot) mapped to node labels and taints. ClusterQueue: a pool of quota per flavor with admission rules and preemption policy. LocalQueue: a namespace's entry point into a ClusterQueue. Cohort: ClusterQueues that may lend unused quota to each other; borrowing and lending limits bound it. Preemption: reclaim borrowed quota for the owner, or evict lower-priority work within a queue; fair sharing weights the split. Kueue decides WHEN a workload may start (it flips `suspend`) and with which flavor; it does not bind pods to nodes (the scheduler does) and does not provision nodes (the autoscaler does).
3. The device plugin advertises an opaque count: "one GPU", any GPU, whole devices only. DRA (resource.k8s.io, GA in 1.34) describes devices with attributes in ResourceSlices; a claim selects by expression (model, memory ≥ 40 GiB, same NUMA node or same PCI root as a NIC), can ask for several devices with constraints between them, can be shared by containers or pods, and lets the driver prepare the device (for example create a MIG slice). It is the path for partitionable and heterogeneous accelerators; fall back to the device plugin where the managed platform or driver is not there yet.
4. MIG: the GPU is split in hardware into up to 7 instances with their own memory and compute; real isolation; fixed profiles, only some GPU models; for small inference models and multi-tenant notebooks. MPS: several processes run kernels concurrently on one GPU with optional memory limits; good throughput for many small jobs of one trusted tenant; a fault in one client can affect the others. Time-slicing: the GPU is advertised as N replicas and contexts take turns; no memory isolation at all, so one pod can OOM the others; fine for development, not for production.
5. (a) Fragmentation: free GPUs scattered, no node with 8 free → bin-pack, defragment by preempting low-priority work, right-size node types. (b) Static per-team quotas: one team idle, another starved → cohorts with borrowing and reclaim. (c) Partial gangs holding GPUs → all-or-nothing admission. (d) Idle allocations: notebooks and debug pods holding GPUs at 0% → idle culling, time limits, MIG slices for interactive work. (e) Allocated but under-used: one small model per whole GPU, data-loader-bound training → sharing for small models, profiling input pipelines. Also: wrong metric (utilisation of allocated GPUs vs of all GPUs), and capacity pinned to one flavor nobody wants.
6. The job must tolerate being killed at any moment: checkpoint model, optimizer, scheduler, RNG and data position atomically to durable storage, resume automatically (restart policy, same run id), and handle the 30–120 s preemption notice by saving if possible. Interval: Young/Daly, sqrt(2 × checkpoint cost × mean time between preemptions): 2-minute checkpoints and a 4-hour MTBF give about 31 minutes and ~13% overhead; measure the real reclaim rate per instance type and zone. Keep the head/coordinator on on-demand nodes and shrink checkpoint cost (asynchronous upload, sharded writes) before shrinking the interval.
