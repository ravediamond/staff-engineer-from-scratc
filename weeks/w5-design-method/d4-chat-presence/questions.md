# Questions

1. Why per-conversation sequence numbers instead of timestamps or a global order?
2. How does a client recover after reconnecting to a different gateway?
3. Presence for 50M users: storage, fan-out of presence changes, and what you would not build.
4. Group chat with 200k members: what changes compared with 1:1?
5. End-to-end encryption is required. What does it remove from the server's capabilities, and how do you still do search and spam filtering?

## Model answers

1. Client clocks are unreliable and server clocks skew; a single writer per conversation gives a total order where users actually see order, at no cross-conversation coordination cost. A global order would need a global sequencer, a bottleneck nobody needs.
2. It sends its last received seq per conversation (or a sync token); the server returns everything after it. Delivery state lives in the client's acknowledged pointer, not in the gateway, so gateways are stateless and replaceable.
3. In-memory TTL store (Redis-like) sharded by user: last heartbeat only. Publish only transitions (online/offline), only to users who currently have that contact on screen, and debounce flapping. Do not build exact "last seen" for everyone in real time, or presence for large groups (show counts instead).
4. Fan-out per message becomes huge: switch to pull (members fetch from the group log by seq), push notifications only to active or mentioned members, batched delivery, per-member read pointers stored lazily, admin and moderation controls, and rate limits per sender.
5. The server sees only ciphertext: no server-side search, no content-based spam or ML features, no server-side link previews. Search moves to the client (local index); spam detection uses metadata (rates, graph signals, reports with user-submitted plaintext); previews are generated by the sender's client. Group key management (MLS) adds membership-change complexity.
